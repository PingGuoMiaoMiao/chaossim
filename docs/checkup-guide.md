# 怎么给一个库做体检

`adapters/moonmq/checkup` 是对一个具体库（AMQP 0-9-1 broker）写的。本文说明怎么把它
换到别的库上——以及**哪些部分可以照抄、哪些必须重写**。

先说结论：**形状可以照抄，规则不行。** 换一个域（从消息中间件换到事务引擎），判定函数要按那个域的语义重写——但“观测 → 纯判定 → 结论”这个形状、以及负向对照的做法，原样保留。`adapters/moontxnkit` 就是按这个原则做的第二个域（10 项），它的判定函数与 broker 那 11 条没有一个相同。

## 一、11 个问题（broker 域的例子，供参照）

这些问题的答案只有"通过/风险"，与具体库无关。判定函数在
`adapters/moonmq/adapter/checkup_rules.mbt`，直接复用：

| # | 问题 | 判定函数 |
| --- | --- | --- |
| 1 | 同一次投递被确认两次，第二次会被拒绝吗 | `judge_double_ack` |
| 2 | 消息被重投后，旧 tag 还能被确认吗 | `judge_ack_after_requeue` |
| 3 | 标注重投之后，消息真的回到队列了吗 | `judge_requeue_returns` |
| 4 | 标注丢弃之后，消息真的消失了吗 | `judge_discard` |
| 5 | 预取上限生效了吗（未确认时不再投递） | `judge_prefetch` |
| 6 | 取消消费者时，未确认消息回到队列了吗 | `judge_cancel` |
| 7 | 有未确认消息时，删队列被拒绝了吗 | `judge_delete_refused` |
| 8 | 批量确认里有坏 tag 时，好的那些被误消费了吗 | `judge_ack_many` |
| 9 | 另一个会话能确认我的投递吗 | `judge_isolation` |
| 10 | 扇出到多个消费者时，每个都收到了吗 | `judge_fanout` |
| 11 | 通配符只匹配该匹配的 key 吗 | `judge_topic` |

如果你的库不是消息中间件，第 5–11 条可能要换成你这行的对应语义，但**判定函数的形状
不变**：接受一个观测事实，返回"这算不算缺陷"。

## 二、观测层（必须重写）

每个检查项做三件事：**准备状态 → 触发一次操作 → 把事实交给判定**。

以第 1 条为例（moonmq 版本）：

```moonbit
let (b, q) = fresh("chk.ack")     // 准备：一个新 broker + 队列
put(b, q, "a")                    //       投一条消息
let tag = take(b, q)              //       取出来（产生一次未确认投递）
let _ = b.ack(tag)                // 触发：确认第一次
let ok = b.ack(tag) is Ok(_)      // 触发：确认第二次
verdict_of(                       // 判定：交给纯函数
  name, question,
  judge_double_ack(ok),
  why_double_ack(ok),
)
```

换库时要改的只有前三步。**不要**在观测层写 `if ... risk(...)`——那会把判定和观测重新
黏在一起，负向对照就测不到它了。

## 三、怎么知道自己的体检项没写错

两件事必须做，缺一个这份报告就不可信：

1. **给判定喂坏输入**：`checkup_wbtest.mbt` 里，每条规则都要有用"故意错的观测"跑一次的
   用例，要求返回风险。没有这一步，"11 项全通过"和"检测器坏了"无法区分。
2. **给观测喂一个你真的知道答案的库**：先拿一个**你确定有问题的**行为跑一遍，确认它报
   风险。moonmq 这一版**没做第 2 步**——所以本项目的报告只敢声称"判定层已验证"。

## 四、诚实边界（照抄到你的报告里）

一份体检报告必须写清楚它没覆盖什么，否则读者会把它当保证：

- 单进程内仿真，不模拟真实网络（不切 TCP、不改磁盘）；
- 检查的是**故障下的语义**，不是性能、不是安全；
- 通过 ≠ 正确：只说明这 11 条路径没发现问题；
- 观测层是否灵敏，取决于你有没有做过第 2 步对照。

## 五、多久能做出来

moonmq 这一版（11 项 + 并发扫描 + 报告生成）大约是一个下午的迭代量，其中**大部分时间
花在 MoonBit 的语法细节和格式器差异上**，不是花在测试设计上。如果你要接一个新库，先
确认它同时具备：可确定性构造、可注入故障的入口、以及能从外部观察到的事实（计数、标签、
统计）——三者缺一，观测层就写不出来。
