# v0.3 spike 裁决：`moonbitlang/async` 运行时级确定性调度可行吗？

- 日期：2026-11-19
- 结论：**不可行（用当前公开 API）**。chaossim 维持"驱动 sans-I/O 状态机"的范围。
- 证据来源：本机 `.mooncakes/moonbitlang/async`（随 `moonbitlang/async` 依赖下载的
  源码），逐条给出文件与行号，可自行核对。

## 1. 好消息：确实存在可插拔事件循环

`src/external_loop_integration/external_loop.mbt` 定义了：

```moonbit
pub(open) trait ExternalEventLoop {
  fn poll(Self, timeout? : Int32) -> Unit raise
  fn get_wakeup_callback_for_foreign_thread(Self) -> FuncRef[() -> Unit]
  fn terminate(Self) -> Unit raise
}
```

`src/internal/event_loop/event_loop.mbt:115` 提供 `set_external_event_loop(extloop)`，
官方测试（`external_loop_test.mbt`）里还有一个 `MainLoop` 示例，把 TCP 接受连接、
自定义事件、定时器混在一个外部循环里跑通。**所以"接管事件循环"这件事本身是官方支持的。**

## 2. 但是三条硬约束让"确定性"不成立

### 2.1 时间不可注入：定时器锚在墙钟

```moonbit
// src/internal/event_loop/timer.mbt:28
let expire_time = now() + duration.to_int64()

// src/internal/event_loop/event_loop.mbt:306
let timeout = first_timer.expire_time - now()
```

而 `now()` 是固定实现：

```moonbit
// src/internal/event_loop/event_loop.mbt:188-189
pub fn now() -> Int64 {
  @env.now().reinterpret_as_int64()
}

// 同文件 :195，native 上直接是 C FFI 导入
pub fn now() -> Int64 = "moonbitlang/async" "time/get_ms_since_epoch"
```

外部循环能决定 `poll` 等多久，但**改不了 `now()`**。于是 `sleep`/超时的真实
截止时刻仍由墙钟决定：同一个种子跑两次，协程在"哪一次 tick 醒来"可能不同。
chaossim 的招牌是"逐字节可重放"，这条直接否掉。

### 2.2 协程调度器是私有的，顺序不可控

```moonbit
// src/internal/coroutine/scheduler.mbt
priv struct Scheduler { ... run_later : Deque[Coroutine] ... }
```

公开面只有 `current_coroutine()` / `has_immediately_ready_task()` / `reschedule()`
/ `all_coroutines()`——**没有"按我给的顺序执行"或"注入调度决策"的入口**。
`reschedule()` 按 FIFO 跑完当前一轮，顺序由运行时内部决定。

### 2.3 仅 native 可用，且唤醒回调有严格限制

```moonbit
// src/internal/event_loop/event_loop.js.mbt:25
let _ : (&@external_loop_integration.ExternalEventLoop) -> Unit = ignore   // JS 后端是空实现
```

trait 文档还明确要求唤醒回调"只能直接调用 C FFI，且该 FFI 不得做任何 MoonBit
引用计数操作"——这是为跨线程 GUI 唤醒设计的，不是为仿真。

## 3. 那么 chaossim 还能往哪走？

结论不是"什么都做不了"，而是**能做的和能宣称的必须分层**：

| 层次 | 可行性 | 能宣称什么 |
| --- | --- | --- |
| sans-I/O 状态机（当前范围：moon-mqtt `ClientCore`、MoonAMQP1 `Endpoint`） | ✅ 已实现 | **逐字节可重放**，故障下记账可核对 |
| 真实 async 程序的**事件注入**（用 `set_external_event_loop`，native only） | ⚠️ 可行但半确定性 | 只能说"按脚本投递事件、观察不变量"，**不能说可重放** |
| 真实 async 程序的**确定性虚拟时间 + 调度顺序控制** | ❌ 当前 API 不支持 | 无 |

因此本项目不做第 3 层，也不把第 2 层包装成第 3 层。若将来 `now()` 变为可注入
（例如提供时钟源配置），第 3 层才重新评估——届时改动点是 `now()` 与
`Scheduler` 的可见性，不涉及本项目的内核。

## 4. 这次 spike 的副产品

- 确认了两个靶子的选型正确：它们的**纯计算核心**正是为了绕开这些运行时约束
  （moon-mqtt 的 `core/` 四后端可测、MoonAMQP1 明确 sans-I/O 无内置 broker）。
- README 里 v0.3 的"风险前置"条目现在有了带行号的裁决，而不是一句"暂不支持"。
